# AIROOM 技术说明

> 面向维护者和开发者。日常使用请看项目根目录的 [README](../README.md)。

AIROOM 是本机多成员 AI 桌面工作台，把成员对话、公开过程、任务审批、文件差异和成果验收放在一个窗口里。成员通过各自的原生执行端和独立登录工作，也可以设置人物卡、模型、思考程度和长期记忆。

## 技术栈

成员原始立绘随源码保存在根目录（`Claudia.webp`、`GPTIA.webp`、`ds.webp` 等）；界面实际使用的人物与房间素材位于 `src/renderer/assets/`。下载源码时会一同取得这些文件。

| 层 | 选型 | 用途 |
| --- | --- | --- |
| 桌面外壳 | Electron 44 | 窗口、托盘、系统对话框、通知、`safeStorage` 加密、`utilityProcess` 后台进程 |
| 界面 | React 19、TypeScript、lucide-react 图标 | 单页应用；样式为手写 CSS，颜色、字号、圆角统一用 CSS 变量，支持浅色和深色 |
| 后台 | Node.js 24（Electron 内置） | 执行服务：调度成员程序、维护流程状态、读写数据 |
| 数据库 | SQLite（Node 内置 `node:sqlite`），WAL 模式 | 所有业务数据和事件流 |
| 网络 | undici | 按设置走系统网络或显式代理，用于下载和额度查询 |
| 成员程序 | Claude Code、Codex CLI、DeepSeek Harness，以及 Qoder、Kimi、OpenCode、ZCode、Gemini、Cursor 等清单程序 | 每位成员背后的真实执行端 |
| 构建 | esbuild（主进程、预加载、后台）、Vite（界面） | 产物输出到 `dist/` |
| 打包部署 | electron-builder（NSIS 安装包、便携包），PowerShell 部署脚本 | 日常运行版直接部署到 `%USERPROFILE%\AIROOM` |
| 测试 | `node:test` + tsx、Playwright（浏览器与 Electron） | 单元、集成、界面冒烟、桌面冒烟 |

## 整体架构

AIROOM 由三个进程组成。界面只负责显示和发起请求，所有业务都在后台执行服务里完成。

```
┌──────────────────────── Electron 主进程 (src/main) ────────────────────────┐
│ 窗口与托盘 · 单实例锁 · 系统对话框 · 通知 · safeStorage 密钥 · 资源协议       │
│ ipcMain('airoom:invoke')：方法白名单 + 分方法超时，转发给执行服务             │
└───────▲──────────────────────────────────────────────────────┬──────────────┘
        │ contextBridge (window.airoom)                         │ MessagePort
┌───────┴────────────┐                                ┌─────────▼───────────────────────────┐
│ 界面 (src/renderer) │ ◀──── 快照推送 (push) ─────── │ 执行服务 utilityProcess (src/backend) │
│ React 单页          │ ───── invoke(method, params) ─▶│ Engine：调度、流程、讨论、圆桌        │
└────────────────────┘                                │ Store：SQLite 实体表 + 事件表         │
                                                      │ Adapter：每种成员程序一个适配器       │
                                                      └─────────┬───────────────────────────┘
                                                                │ 子进程 (stdio)
                                         ┌──────────────────────▼──────────────────────────┐
                                         │ 成员程序：claude -p stream-json · codex app-server │
                                         │ · ACP 程序 (DSH / Qoder / Kimi / OpenCode / …)     │
                                         └──────────────────────────────────────────────────┘
```

- **主进程**（`src/main/main.ts`）
  - 启动时检查完整性级别（低完整性环境拒绝启动），恢复上次中断的资料恢复；
  - 然后创建窗口和托盘，用 `utilityProcess.fork` 启动执行服务；
  - 通过 `MessageChannelMain` 把一个消息端口交给执行服务；
  - 登录令牌、API Key 由 `safeStorage`（Windows DPAPI）加密保存，连接时只交给执行服务；
  - 执行服务意外退出时自动重启，并标记未完成的运行“结果待核对”。
- **预加载**（`src/main/preload.ts`）只暴露 `window.airoom.invoke`、事件订阅和少量文件工具，界面拿不到 Node 能力。
- **请求**：界面调用 `invoke(method, params)` → 主进程检查方法是否在白名单内、按方法设置超时（如备份 10 分钟、下载 20 分钟）→ 经消息端口转给执行服务 → 返回结果。
- **状态**：执行服务每次变化后推送一份完整快照（`snapshot-sync.ts` 带序号和去重），界面始终渲染最新快照；发现漏包时请求全量重同步。较大的数据（历史消息、事件、日志）按需单独读取。
- **资源**：头像、立绘、附件、生成的图片通过自定义协议 `airoom-asset://` 读取，不暴露真实路径。

    backup*.ts           备份写入与恢复

## 关键实现

### 数据存储

- 数据库是 `data/airoom.sqlite`，只有两张核心表：
  - `entities(entity, id, value)`：所有业务对象都以 JSON 存在这里，按 `entity` 分类，例如 `projects`、`sessions`、`runs`、`room_messages`、`flow_tasks`、`roundtable_topics`；
  - `events`：每次运行的事件流（文字增量、工具调用、状态），按会话和运行建索引。
- 开启 WAL 和 `busy_timeout`，对消息所在话题、正在发言的消息建了表达式索引。
- 模式变化通过“读取时兼容 + 启动时迁移”处理，不做破坏性迁移。
- 消息之外的文件放在数据目录的子目录：
  - `assets`：人物图片；
  - `attachments`：附件和生成的图片；
  - `workspaces`：工作副本；
  - `checkpoints`：还原点；
  - `native`：各成员程序的独立登录与会话目录；
  - `members`：下载的成员程序版本。

### 成员程序接入（适配器）

每种成员程序实现同一个 `Adapter` 接口（`src/shared/types.ts`）：

- `probe`：检查连接和登录，不发模型请求；
- `start`：执行一轮，返回结果，或者“已停止 / 结果未知”；
- `stop`：立即停止；
- `steer`：运行中补充要求；
- 可选的额度与余额查询。

三类接法：

| 接法 | 适用 | 实现 |
| --- | --- | --- |
| Claude Code 原生流 | Claude | `claude -p --input-format stream-json --output-format stream-json`。工具审批通过随包的 MCP 服务（`claude-permission-mcp.cjs`）回到 AIROOM |
| Codex app-server | Codex | `codex app-server` 的 JSON-RPC：线程、回合、审批、图片生成；权限映射到 Codex 的沙箱与审批取值 |
| ACP（Agent Client Protocol） | DSH、Qoder、Kimi、OpenCode、ZCode、Gemini、Cursor 等 | 通过 stdio 建立 ACP 会话，支持会话恢复、模型和思考程度配置、权限请求 |

- **程序版本**：清单里的成员程序用随包的 npm 安装到 `data/members/<程序>/<版本>`。安装后按 npm 的 lock 文件核对完整性，旧版本保留可回退；正在使用的版本不能删除。
- **账号**：每个程序的登录目录都在 `data/native` 下单独存放，启动时清掉宿主环境里的 `CLAUDE*`、`ANTHROPIC*`、`CODEX*`、`OPENAI*` 等变量，不借用其他软件的登录。
- **配置**：每次运行记录“请求的模型 / 思考程度”和“程序实际报告的值”（`requestedConfig` / `effectiveConfig`），界面据此显示实际模型。

### 运行调度与“不重发”

- 一次运行（`run`）从“已准备”到“已送达”再到“结束”，状态都写进数据库。
- 只要无法确认请求有没有送到或有没有完成，就标为 `unknown`。例如进程被杀、程序没有输出就结束、重启时发现未完成的运行。
- 处于 `unknown` 的运行**不会自动重发**，由“待你处理”提示用户核对。
- **对话类运行**（工位、茶歇室）复用常驻进程：`runtime-pool.ts` 给每个房间会话一个串行租约，空闲进程不占执行名额，过一段时间自动退出。项目任务每次结束都关闭进程。
- **进程管理**：成员程序都由 `process-supervisor.ts` 启动并登记归属，放进 Windows Job Object，退出时连同它派生的子进程一起结束，不留孤儿进程。
- **中止**分三级：当前对话、某位成员、全部。成员级中止会先跳过已删除项目留下的房间状态，确保真正的运行被停下。

### 讨论（茶歇室、会议室、圆桌审议）

- `room-discussion.ts` 是每个房间一个的状态机，阶段包括：自由讨论、举手、等你点名、收尾、整理纪要、空闲。
- **成员回复协议**：发给成员的提示末尾附一段 `AIROOM_CONTEXT` JSON，成员必须返回 JSON。
  - 带回 `version`、`turn`、`revision`，选择 `speak` 或 `pass`，正文放 `body`；
  - 可以附 `next`（建议谁接话）和 `questions`（向谁提问）；
  - 回合号和版本号对不上的回复会被丢弃，防止过期发言覆盖新状态；
  - 格式不合规时会进行一次“格式补正”，并单独计数。
- **已读位置**：每位成员都记着已读到哪条消息，长讨论里只把新消息当未读，并定期补发规则背景。
- **压缩上下文**：由一位成员写摘要，之后成员从摘要继续，原消息保留。新话题可以继承摘要。
- **会议纪要**：材料里附上本次参会者名单，纪要只写参会者。

### 项目流程

- 状态分散在多个实体里：
  - `flow_*`：方案、轮次、任务、操作、决定；
  - `project-flow*.ts`：方案确认、派发、复核、整合检查、验收、写回、恢复，按职责拆分；
  - 每次修改都带 `expectedRevision`，版本不对就拒绝，界面提示刷新。
- **派发**：依赖满足、成员空闲时，任务开始执行。可以“暂停派发”，已在做的任务会做完。
- **复核程度**：控制哪些任务和轮次需要另一位成员检查。复核意见、补正和重试都会计入调用次数。
- **运行中补充**：送到成员正在做的任务，有“已送达 / 已应用 / 结果待核对”三种回执。

### 工作副本与写回

- **Git 项目**：用 `git worktree add --detach` 建立独立工作区。
- **非 Git 项目**：复制一份目录。
- **讨论阶段**一律只读；**执行阶段**在副本里写。
- **写回前的检查**：对比原文件指纹，发现冲突就停下来列给用户，不覆盖。
- **写回过程**：第一次写入前先保存原文件的原始字节，所以“撤销最近一轮”可以连同原文件一起恢复；撤销失败会把原文件回滚。
- **路径校验**：检查每一级目录有没有符号链接或目录联接，防止副本里的链接把写入带到外面。

### 圆桌与独立评审

- `joint-review.ts` 管理评审的各个阶段：
  - **独立**：每人一份，互相看不到；
  - **互评**：只看别人的版本，候选匿名，用字母代替；
  - **作者答复**；
  - **汇总**：汇总者看到的是编号，不是作者名字，避免偏向自己的稿子；
  - **验证**：有影响验收的分歧时，派给非作者核实。
- `roundtable.ts` 在评审完成后开启审议讨论，并管理：
  - 选稿：只能采用已完成的候选；
  - 纪要和确认结论；
  - 带回项目：以材料形式送进项目会议室。
- 界面显示结论时，会把候选编号换成“某某的版本”；存储的原文保持不变。

### 安全与隐私

- 密钥只存在 `safeStorage` 加密文件里，运行时登记到脱敏表，日志和诊断导出前统一脱敏。
- 预加载只暴露白名单方法；渲染进程开启上下文隔离和沙箱。
- 默认“自动工作”权限：命令自动批准、可以联网、不限制文件范围。实际影响范围靠工作副本控制，但副本**不是**操作系统级隔离边界。权限页可以收紧。
- 不修改系统代理、DNS、防火墙和网卡，不申请管理员权限。

### 备份与恢复

- 备份由独立入口 `dist/backup.mjs` 写入，应用和部署脚本共用。
  - **包含**：数据库一致性快照、人物图片、附件，以及带 SHA-256 的清单；
  - **不包含**：登录凭据、密钥、程序版本、工作副本、还原点。
- 只保留最新一份：新备份写入并校验成功后，才删除旧的。
- 恢复分三步：准备（校验并预览）→ 替换前再备份当前资料 → 替换。中途失败会回滚；启动时如果发现上次恢复中断，也会先回滚。

## 构建、打包与部署

| 命令 | 作用 |
| --- | --- |
| `npm run build` | esbuild 打包 `main.mjs`、`preload.cjs`、`worker.mjs`、`backup.mjs` 和 Claude 权限服务；Vite 构建界面；复制图标、进程管理脚本和第三方声明 |
| `npm start` | 用当前构建启动 |
| `npm run dev` | 开发模式 |
| `npm run package` | electron-builder 生成 NSIS 安装包和便携包 |
| `npm run package:green` | 从源码和 Electron 依赖构建 `release/win-unpacked`，生成可直接解压运行的 ZIP、SHA-256 校验文件和打包记录；无需预先安装 AIROOM |
| `npm run deploy` | 构建并部署到 `%USERPROFILE%\AIROOM`，见下文 |

部署分三步：

1. `prepare-deployment.mjs` 构建并生成文件清单和哈希；
2. `deploy-runtime.ps1` 复制 Electron 运行时和应用，核对运行依赖，创建桌面和开始菜单快捷方式；
3. 写入 `deployment-receipt.json`，内容包括来源提交、目标目录和各文件哈希。

加 `-Backup` 参数会先备份日常资料，备份失败就不替换任何文件。部署前需要从托盘彻底退出 AIROOM。

`package:green` 与本机增量部署分开：前者使用 electron-builder 创建新运行目录，后者复用已有安装版的已校验外壳。分发打包需在 Git 仓库中执行，并先提交源码变更；脚本拒绝将未提交的受跟踪改动标为正式分发。已有同名 ZIP 时会停止，避免覆盖已发布文件。

绿色包只包含 Electron、应用和生产依赖，不包含开发者资料或预装的成员 CLI。完整解压后运行 `AIROOM.exe`，首次在设置中下载并登录所需成员。资料默认仍写入 `%USERPROFILE%\.airoom\data`，与同一 Windows 用户下的安装版共用；它是免安装程序包，用户资料不会随解压目录迁移。

公开分发地址：[GitHub Releases](https://github.com/tonyAmadeus/offAice/releases)。绿色 ZIP 可在浏览器下载，不需要 Git 或开发环境。安装包使用带目录选择的 NSIS 安装向导，并提供 `Uninstall AIROOM.exe`；卸载默认保留个人资料。

## 测试体系

| 层级 | 位置 | 方式 |
| --- | --- | --- |
| 单元与集成 | `tests/*.test.ts`（约 130 个文件，1,000 多项） | `node:test` + tsx。用假的成员程序驱动真实的 Engine 和 Store，覆盖调度、讨论、流程、圆桌、备份、草稿、恢复等 |
| 界面冒烟 | `tests/ui/*-smoke.mjs`（40 组） | `ui-test-server.mjs` 启动真实 Engine，成员程序用模拟实现，Playwright 在浏览器里逐步操作并断言 |
| 桌面冒烟 | `scripts/desktop-smoke.mjs` | 用 Playwright 启动真实 Electron 构建：首次启动、消息端口 RPC、私有方法拒绝、持久化、资源协议、单实例、托盘、加密存储、执行服务崩溃恢复、备份恢复 |
| 真实账号诊断 | `scripts/real-account/` | 使用真实登录、消耗额度，默认不运行，见下文 |

测试环境：
- 每个测试进程都用独立的临时数据目录，并清除宿主的账号环境变量；
- 测试子进程同样放进 Windows Job Object，结束时连同子进程一起清理；
- 界面截图写到 `.test-cache`。

## 打开与配置

日常双击桌面或开始菜单的 AIROOM 图标，程序位于 `%USERPROFILE%\AIROOM\AIROOM.exe`；项目根目录的 `Start-AIROOM.cmd` 启动同一份桌面安装。关闭窗口会留在托盘，托盘可中止全部工作或彻底退出。同一 Windows 用户只运行一个主窗口，再次启动会唤起已有窗口。

日常与开发入口默认都使用 `%USERPROFILE%\.airoom\data`，可用 `AIROOM_DATA_DIR` 明确指定其他目录。不同入口共用单实例锁，切换数据目录前应从托盘退出；隔离验证始终使用临时目录。便携包每次启动会解压，日常优先使用安装后的解压版。

1. 在“设置”检查成员连接，缺少执行端时下载或添加程序，未登录时走对应官方登录入口。
2. 在网络页按本机实际出口选择系统网络或显式代理。AIROOM 不修改 Windows 代理、TUN、DNS 或网卡；网络模式应与当前系统配置一致。
3. 根据任务进入工位、圆桌或项目会议室，再选择成员、模型和复核程度。

Codex、Claude、DSH 的账号分别保存在 `data/native/codex/home`、`data/native/claude`、`data/native/dsh`；不复制其他桌面应用的凭据。DSH 使用独立后台，无需保持 DSH 桌面客户端运行。订阅与 API 登录按所选执行端和登录方式区分，失败不会自动切换到 API 计费。密钥由 Windows 系统加密保存。

## 选择工作方式

| 入口 | 适合的任务 | 如何完成 |
| --- | --- | --- |
| 成员工位 | 单人问答、起草、整理资料、小任务 | 在当前话题继续；个人文件夹直接读写，其他目录使用任务副本 |
| 圆桌 | 多个独立方案、比较意见、共同评审 | 查看候选与分歧，选择方案并确认结论，需要时把结论带回项目 |
| 项目会议室 | 多任务协作、分轮交付、需要验收的工作 | 讨论要求 → 选负责人起草方案 → 确认方案 → 执行与复核 → 验收写回 |
| 茶歇室 | 闲聊、讨论、会议、明确提出的绘图 | 按讨论状态接话，需要时整理会议纪要 |

项目会议室的复核程度说明检查范围和调用开销：**深入复核**逐项核对任务和每轮成果；**标准复核**核对每轮汇总成果；**快速推进**由你逐轮选择复核或验收。可在确认方案时调整每轮设置，最终成果仍由你验收。修订、重试和额外复核会增加调用。

项目和圆桌进度区突出当前下一步，例如核对中断结果、查看方案、处理决定、比较候选或查看成品。点击“查看”会展开并定位对应内容；实际确认、选择或验收仍在内容卡片上完成。

工位标题持续显示实际工作位置及“直接读写 / 任务副本 / 只读”状态，可打开当前工作位置。项目标题标明原目录；会议讨论只读，任务在独立副本执行，验收后写回项目。执行期间产生的改动保留供检查，投递未知时先核对，不自动重发。

## 话题、草稿与讨论

工位、茶歇室的新话题未手动命名时，用第一条实际用户消息的前 20 个字符起名并合并空白，不增加模型调用；手动命名和已有历史名称保留。

工位、汇报、茶歇室、项目会议室及圆桌共用消息输入框的草稿保存：文字、附件、回复对象和任务用途按话题分别保留，切换成员、文件夹或重启后可继续编辑。打开草稿不会发送消息。发送成功后清除已发送的版本；等待发送回执时继续输入的新内容保留。暂时无法写入本机资料时会显示提示并提供重试。备份恢复后读取恢复后的草稿，旧缓存不会覆盖它。

Enter 发送，Shift + Enter 换行；`@` 可选择成员，对消息可点“回复这条”。话题记录支持当前话题与只读归档、加载更早消息、导出和压缩上下文。压缩会使用一次成员调用，原消息保留。清空或删除需明确确认。

茶歇室的闲聊按在场成员和实际内容接话；开会默认让在场成员依次发言一轮，然后等你补充或决定。举手模式会增加独立的举手调用，状态栏显示实际预算和剩余发言。需要你回答的问题会等待回应；整理会议纪要也会使用成员调用。只有原生执行端返回的正文、公开摘要和活动会展示。

“暂停接话”在当前发言结束后暂停；“中止当前对话”“中止成员”“全部中止”请求立即停止。人工暂停后需要明确继续。重启、缺失回执或投递未知都不会自动重发。使用 Codex 的成员可按明确要求生成或修改图片，结果保存在本机。

调用次数分别显示**累计尝试、已发出、已完成**，未发出失败、撤回和结果未知单独列出。圆桌的“准备阶段基础预计”只包含独立意见、互评和汇总等准备步骤；公开后的审议、举手、纪要与格式补正另计。次数不等同于订阅账单，额度和费用只显示执行端实际返回的数据。

旧接力 / 旧讨论执行入口已退役，已有协作阶段和结果仍保留供阅读。后续共同评审使用圆桌，协作交付使用项目会议室。

## 权限与成员程序

默认采用自动工作：新工作会话允许写入，命令自动批准，允许联网，文件范围不限制；真实提问仍会等待你的回答，操作会记录，并保留一键停止和时限。已有只读会话继续只读。工作副本用于差异核对和回退；完全访问时执行端仍可能修改副本外文件，副本不是操作系统隔离边界。

可在权限页调整命令、文件范围和工具联网，或恢复自动工作设置；模型、账号路径及系统网络配置不随之改变。关闭工具联网不等于操作系统断网，模型对话仍需要服务端连接。不申请 Windows 管理员沙箱。

人物卡可设置头像、立绘、称呼、个性、记忆、模型和思考程度。模型配置按话题、人物卡、全局设置依次取值；人设不改变权限。保存人物卡后修改生效，取消保留原设置。

执行端清单可下载、检测、更新、切换及清理版本；旧版本保留作为回退。当前选用或运行中的版本不能删除，安装与切换按空闲状态处理。聊天与登录资料独立保存，恢复原生上下文失败会显示实际错误。DSH 需要独立 Node.js，可用 `AIROOM_NODE_EXE` 指定，缺失时界面会说明原因。

Claude 在“仅限工作区”模式下显式读取当前目录的 `CLAUDE.md` 与 `.claude/CLAUDE.md`，合计最多 64 KiB，不展开父目录、嵌套规则或引用；“不限制”模式由 Claude 原生加载项目和用户设置。过程记录显示实际加载方式。

## 资料、备份与恢复

SQLite 数据库、消息、人物图片、附件、原生会话目录和工作副本保存在本机。意外中断后可重启执行服务，或从托盘退出后重开；记录保留，中断工作不会自动继续。

“设置 → 工作台”提供手动备份、列表、校验预览和恢复。数据库、人物图片与附件进入备份；登录凭据、密钥、程序版本、任务工作副本和还原点不进入备份。手动、部署前与恢复前备份共用**最近 1 份**规则，只有新备份保存并校验成功才清理旧备份。

恢复前需预览并明确确认，替换前再备份当前资料，失败时回退。当前登录和密钥保留；恢复的旧项目会话只供阅读，自动功能保持暂停，需要核对后重新启用。

## 开发与验证

需要 Windows 及 Git；开发建议使用 Node.js 26。锁定的 npm 12 要求 Node.js `^22.22.2 || ^24.15.0 || >=26.0.0`，不要仅按“Node 22 以上”判断兼容。非 Git 项目使用独立目录副本。构建依赖锁定，执行端版本由用户选择更新。

开发依赖统一安装在项目根目录的 `node_modules`。同一版本的协作目录可用目录联接共用这份依赖；锁文件不同时需按各自版本重新安装。历史工作树只需保留源码、锁文件和验收记录，重复依赖、构建输出及隔离测试配置可以清理。桌面安装目录自带的运行依赖用于独立启动，应随安装版本保留。

```powershell
npm ci
npm run build
npm start
npm run verify
```

`npm run verify` 依次执行类型检查、全部单元与集成测试、全部界面冒烟、桌面构建和真实 Electron 冒烟，任何一步失败都会停止。每个测试进程使用独立的、未登录的临时用户目录，清除继承的宿主会话和账号变量，**绝不碰日常的 `%USERPROFILE%\.airoom\data`**；截图写到 `.test-cache`。会使用真实登录、消耗额度的测试放在 `scripts/real-account/`，需要账号所有者同意，并从托盘彻底退出 AIROOM 后，加 `--use-real-account --app-closed` 才能运行。

从 AI 宿主启动程序时应清除继承的 `CLAUDE*`、`ANTHROPIC*`、`CODEX*` 等宿主变量；AIROOM 启动成员时也会过滤这些变量。普通验证不使用真实账号，也不代表真实模型端到端验收。

## 部署补充说明

- `npm run build` 构建开发程序。
- `npm run deploy` 构建并更新本机日常运行版，生成部署记录与哈希；先从托盘退出，运行中的程序或未完成的资料恢复会阻止部署。默认不备份，显式添加 `-- -Backup` 才备份资料。
- `npm run package` 生成 Windows 安装包、便携包、构建记录和部署提示，用于分发；打包成功不代表日常安装已更新。
- 设置的工作台页显示运行版本、来源提交及构建和部署时间。完成实际使用验收后可记录“这个版本没问题”。

部署保留资料、登录、备份及恢复文件；不会自动更新便携包或替你确认真实账号验收。
