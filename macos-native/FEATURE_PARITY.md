# offAice 原版 vs. AIROOM Native — 功能對照（本輪）

評估原則：**已實作**表示有對應實際程式碼且完成核心測試；**部分**表示流程可用但缺原版完整能力；**未完成**表示沒有可操作後端。所有 Native macOS 實機功能仍需由使用者編譯驗收。

| 功能 | 原版 offAice | Native 本輪後 | 尚缺／限制 |
| --- | --- | --- | --- |
| 原生桌面 UI／人物／暖色佈景 | Electron | **已實作** SwiftUI | 未做逐像素回歸 |
| Codex 官方執行端 | App Server | **已實作** App Server | 真實 macOS 登入、Session 行為待驗收 |
| Claude 執行端 | 官方 Claude Code | **已實作** 桌面附帶版偵測與 CLI | 登入與版本差異待驗收 |
| 多 AI 共用上下文 | 多房間共享 | **已實作** | 僅成功訊息共享；模型供應商不共用內部 Session |
| 專案會議室：六步流程 | 討論→定負責人→方案（多輪多任務）→執行→驗收→完成；複核程度、暫停／繼續、看板、成員匯報、@ 點名三種用途、開始新的一段工作 | **已實作** | 不同成員、互不依賴、預計修改檔案不重疊的任務同時進行（每專案可設 1–3 項，一位成員一次一項；沒寫檔案的任務單獨做），每項任務獨立副本、合併進本輪副本時檢查衝突，驗收通過才寫回；深入複核最多退回 2 次；作者可對複核意見提出異議，由你逐條裁定（支持作者返還一次退回，每項任務最多 2 次；維持複核則必須修正），附言與驗收意見也交給複核者；成員額度用完時只停那位成員的工作（也不會再叫 TA 複核或修正，任務停在原處等），記下預計恢復時間、到點通知，按「接著做」或換人接手，不自動重送；退回後的修正任務沿用成員原本的檔案清單，看板顯示每項任務的檔案。並行、異議（支持作者）、額度等待與換人接手、修正任務沿用檔案都已實際跑過（額度用完是用測試腳本模擬 Claude 回報用量上限，不是真的用完）；「維持複核」只有單元測試（實測時作者都直接照改，沒有提出異議）；三位以上成員時由負責人裁定的做法未實作（目前只有兩位成員，裁定一律交給你） |
| 圓桌：評審／比稿／方案比較 | 各自準備、公開、互評、匯總問題清單、審議、並排比較採用、會議紀要、確認結論、帶回專案 | **已實作** | 審議沿用茶歇室開會引擎（舉手、點名）；成員依序準備，未平行執行 |
| 延續各家 CLI 對話 | 成員沿用自己的原生 Session | **已實作** | 工位每個話題一段 CLI 對話；茶歇室／圓桌審議／專案會議室每位成員各一段，只補送新內容；無法延續時（且確定未送達模型）自動改用完整歷史重開一次；圓桌各自準備、互評、紀要、摘要等單次任務仍為獨立呼叫 |
| 茶歇室：閒聊／開會 | 自由接話、@點名、提問留存、舉手、點名、會議紀要、壓縮、匯出、清空、新話題延續 | **已實作** | 依原版發言協定（speak/pass/react/ask_user/propose/accept/reject）；閒聊每則訊息最多 16 次發言後暫停；「畫圖」請 Codex 生成或修改圖片（可附參考圖、以這張修改、另存、拷貝），已實測生成與修改 |
| 長時間多 AI 互動直播 | 低頻自動閒聊為主 | **新增直播 MVP** | 設有每場輪數／時數上限；無音訊、直播平台串接 |
| 觀眾插話 | 多人房間中的使用者輸入 | **新增**手動觀眾留言 | 尚未接 Twitch／YouTube API、彈幕審核、優先佇列 |
| 直播長上下文 | 一般聊天室上限 | **新增**每 12 輪 AI 摘要 | 摘要品質尚未實機驗證；原始歷史仍加密保存 |
| 排程任務 | 定時指令／本機提醒 | **新增**每日提醒及房間發言（兩種都已實際觸發） | 尚未有每週日曆 UI、登入項目式背景代理；App 關閉不觸發 |
| 低頻自動閒聊 | 每日觸發與限制 | **完成**：兩位成員依作息、小習慣與關係設定各說一句；時間間隔、每日上限；另有每日開場（每天第一次打開時輪流問候，可提到昨天房間裡確實說過的事） | 成員閒聊已實際觸發；每日開場尚未實際觸發（每天第一次打開才會問候） |
| Claude 交叉唯讀審查 | 可選審查層級 | **已有／部分** | 沒有完整三種審查程度、報告室 |
| 5 小時／每週用量 | 官方查詢 | **已實作** | 真實帳號回應待 Mac 測試 |
| 系統：稱呼、開工前檢查、通知、選單列、全部中止、呼叫次數、待你處理 | 個人資料、去登入、系統通知、托盤、全部中止、累計嘗試／已發出／已完成 | **已實作** | 登入在終端機執行官方 CLI 自己的流程；呼叫次數是 AIROOM 的請求數，不是帳單。待你處理的每一則都可以「忽略」：只隱藏提醒，原本的工作不變，內容有變化時會再出現（已實際操作）；另加「重新顯示已忽略的 n 則」（原版沒有） |
| 成員工位：多話題、草稿、附件、模型與思考程度 | 話題歸檔、自動命名、拖放附件、逐話題模型 | **已實作** | 附件加密保存；Codex 不支援 PDF。工作資料夾：個人資料夾直接修改、其他資料夾在任務副本修改，可應用、撤銷最近一輪（含已寫回的原檔）、丟棄副本 |
| 人物卡細節 | 稱呼、一句話介紹、代表色、預設模型與思考程度、上傳立繪／頭像並調整、從桌面端人設檔匯入、隱藏人物卡、恢復預設資料 | **已實作** | 每位成員可設定怎麼稱呼你（寫進人物設定）、一句話介紹（團隊卡片與首頁）、代表色（色票或自訂，全介面跟著變）、預設模型與思考程度（新話題、茶歇室、圓桌、專案會議室都用；話題裡另外選的模型優先；畫圖請求維持 CLI 預設）、上傳立繪與單獨頭像（加密保存，可調大小、位置與頭像裁切）、從 ~/.claude/CLAUDE.md 或 ~/.codex/AGENTS.md 匯入人設（先完整預覽）、隱藏人物卡（首頁與側欄不顯示）、恢復預設資料（需確認）。除「恢復預設資料」與匯入預覽外都已實際操作過（這台 Mac 沒有 CLAUDE.md／AGENTS.md，只試了找不到檔案的提示）；Codex 回覆標示的模型改為實際要求的模型（Codex 不回報中途更換的模型）。人物形象模板、新增／刪除成員屬於其他執行端，暫緩 |

| 其他 AI（Gemini、Qwen、Kimi 等） | 多執行端 | **暫緩**（使用者決定先不做） | 需要成員改為可選執行端，加上通用 ACP 用戶端 |

## 建議的 macOS 人工驗收

1. 原有 `state.aesgcm` 仍可開啟，舊專案、對話、設定完整。
2. 新建一個茶歇室，選 Claude＋Codex，開始直播 4–6 輪。第二位必須引用第一位真正完成的發言。
3. 插入觀眾留言，下一位 AI 必須能看見該暱稱與訊息；停止後不再觸發請求。重啟 App 不會自動恢復直播。
4. 排程每日提醒、排程房間訊息各測一次；App 關閉後不補發過去的任務。
5. 圓桌產生兩份成功回答，執行互評；手動採用候選並帶回尚未開始的專案，確認不自動寫檔。
6. 新專案經過討論、選負責人、提案、手動核准、副本執行、Claude 審查、人工確認後才寫回。
7. 核對實際配額下降與 CLI 取消結果；高額度開銷前先縮短輪數與間隔做小規模測試。
